# Why use the library

Publishing to one network is a weekend. Publishing to eleven is the rest of the year, and most of that year goes on the parts nobody demos.

## The parts nobody demos

Every network has its own idea of what a post is. X counts characters, wraps every URL to a fixed width, and threads. Telegram takes HTML but only some tags. Discord and Reddit take Markdown, Slack takes its own mrkdwn, Tumblr takes content blocks. Instagram will not accept a local file at all and demands a public URL. WhatsApp needs a pre-approved template for anything unsolicited.

None of that is hard. All of it is fiddly, and all of it drifts.

The library holds one formatter per network, each honouring that network's limits, markup, hashtag placement, and link handling. You write a `Post` once.

## Zero dependencies

`ext-curl` and `ext-json`. That is the whole list.

No HTTP client to conflict with the one your framework already ships, no version range to negotiate, nothing to break on your next major upgrade. It drops into a legacy codebase as easily as a fresh one.

## Publishing that does not throw

`Publisher::publish()` always returns a `PublishResult`. A network being down, a token being stale, or an image being too large gives you a result with `success` false and an `error`, not an exception unwinding through your controller.

Publishing to five networks means five independent results. One failing does not cancel the other four, which is what you want when the request is a user hitting Save.

```php
foreach ($registry->names() as $name) {
    $result = $publisher->publish($post, $name);
    echo $result->success ? "ok: {$result->externalUrl}\n" : "failed: {$result->error}\n";
}
```

## Replaceable everywhere

HTTP, token storage, events, and OAuth each sit behind an interface. Swap the HTTP client for your own, store tokens in your database instead of wherever the default puts them, route events into your existing dispatcher. Adding a twelfth network is one class implementing `PlatformInterface`, with no fork.

## Your credentials, your data

Content goes from your server to the network. Nothing passes through us, nothing is stored by us, and the library works fine on a box with no route to our infrastructure. For a team that cannot send customer content to a third party, that is not a preference, it is the requirement.

## When not to use it

If you want scheduling, a content calendar, analytics, approvals, retries that survive a restart, or the twenty other networks, you would be rebuilding the [Cloud API](/api/overview). Use that instead, or use both: the library for one specific integration, the Cloud for the rest.
