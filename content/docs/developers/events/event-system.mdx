# Event System

Pass a dispatcher to the `Publisher` and it emits an event after every attempt. That is where logging, metrics, and delivery bookkeeping belong, rather than repeated at each call site.

## The contract

```php
use Fopost\Core\Events\Contracts\EventDispatcherInterface;
use Fopost\Core\Events\PostFailed;
use Fopost\Core\Events\PostPublished;

class MyDispatcher implements EventDispatcherInterface
{
    public function dispatch(object $event): void
    {
        match (true) {
            $event instanceof PostPublished => $this->onPublished($event),
            $event instanceof PostFailed    => $this->onFailed($event),
            default                         => null,
        };
    }

    private function onPublished(PostPublished $event): void
    {
        logger("Published to {$event->result->platformName}: {$event->result->externalUrl}");
    }

    private function onFailed(PostFailed $event): void
    {
        logger("Failed on {$event->result->platformName}: {$event->result->error}");
    }
}

$publisher = new Publisher($registry, new MyDispatcher());
```

One method, no base class. If you already have a PSR-14 dispatcher, wrap it in four lines and forward.

The dispatcher is optional. Leave it out and publishing works exactly the same, silently.

## Both events fire

Every attempt produces one: `PostPublished` on success, `PostFailed` on failure. Publishing to five networks emits five events, and a `default => null` arm keeps your dispatcher working when a later version adds a third event type.

## What a listener should do

Write the delivery row, increment a counter, notify a channel. Keep it fast: `dispatch()` runs inline, so a slow listener slows publishing.

Anything genuinely slow, a Slack notification or an email, belongs on a queue. Push a job from the listener rather than doing the work in it.

## In a framework

Both wrappers do this for you:

- Laravel maps them onto native events you subscribe to normally. See [Laravel Events](/sdks/laravel/events)
- WordPress fires `fopost_post_published` and `fopost_post_failed` actions. See [WordPress Hooks](/sdks/wordpress/hooks)

## Not the same as Cloud webhooks

These are in-process PHP events in your own application. The [Cloud API's webhooks](/api/webhooks) are HTTP callbacks from our servers to yours, and are unrelated: the library never calls out to us.
