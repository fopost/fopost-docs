An account is one connected profile on one network, for example a LinkedIn company page or one of several X accounts in the same workspace. Posts target account ids, so this is usually the first call an integration makes. Everything here needs the `accounts` scope.

## List accounts

```http
GET /v1/accounts
```

```bash
curl https://api.fopost.com/v1/accounts \
  -H "X-API-Key: $FOPOST_API_KEY"
```

Each account carries its `id`, `platform`, `username`, display `name`, `avatar`, and whether it is `active`. `name` is the name you gave the account when it has been renamed, and `platformName` is always the network's own. Pass `group_id` to list only the accounts in one [account group](#account-groups). A workspace-bound key sees only that workspace's accounts.

## Rename an account

```http
PATCH /v1/accounts/{id}
```

```bash
curl -X PATCH https://api.fopost.com/v1/accounts/{id} \
  -H "X-API-Key: $FOPOST_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "display_name": "Brand UK" }'
```

The new name shows everywhere the account is listed. It is yours, so a profile refresh from the network never overwrites it. Send `null` or an empty string to go back to the network's name.

## Move to another workspace

```http
POST /v1/accounts/{id}/move
```

```bash
curl -X POST https://api.fopost.com/v1/accounts/{id}/move \
  -H "X-API-Key: $FOPOST_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "workspace_id": "7d2b8c11-4e5a-4a8f-b0d9-3c5e6f7a8b90" }'
```

The account moves with its connection, so nothing has to be reauthorized, and its inbox and analytics history move with it in the same step. You must own both workspaces; any other target answers `404`.

A move is all or nothing. When the account still has records that belong to its current workspace, such as posts, recycling queues, ads, or monitoring rules, the move is refused with `409 move_blocked` and a `blocking_tables` list naming them. A target that already has an account on the same network also answers `409`. The account leaves its account groups, since those belong to the old workspace.

## Account groups

A group is a named set of accounts in one workspace, such as "EU brands" or "Founders". Target a whole group when posting instead of listing every account.

```http
GET    /v1/account-groups
POST   /v1/account-groups
GET    /v1/account-groups/{id}
PATCH  /v1/account-groups/{id}
DELETE /v1/account-groups/{id}
PUT    /v1/account-groups/{id}/members
```

```bash
curl -X POST https://api.fopost.com/v1/account-groups \
  -H "X-API-Key: $FOPOST_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "workspace_id": "7d2b8c11-4e5a-4a8f-b0d9-3c5e6f7a8b90",
    "name": "EU brands",
    "account_ids": ["3a9f1d20-6c77-4b2e-9a01-8f5d2c3b4e10"]
  }'
```

Each group carries its `id`, `name` and `account_ids`. `PUT …/members` replaces the member list with the `account_ids` you send. `PATCH` renames the group, and `DELETE` removes the group while its accounts stay connected. Every account must belong to the group's workspace.

To post to a group, pass `account_group_id` on [create post](/api/publishing). Each account publishes once, even when it is also listed in `accounts`.

## Connecting an account

Connecting is an OAuth handshake with the network, so it happens in a browser. Your own accounts connect in the dashboard under **Accounts → Connect**. For your users' accounts, mint a hosted connect link and hand it to them.

`POST /v1/accounts` exists for the handful of networks that authenticate with credentials you already hold rather than an OAuth redirect.

## Hosted connect links

A connect link is a single-use URL that lets one of your end users connect a social account into your workspace, with no FoPost login and under your branding. Use it when your product needs its users' accounts, not yours.

```http
POST /v1/connect-sessions
```

```bash
curl https://api.fopost.com/v1/connect-sessions \
  -H "X-API-Key: $FOPOST_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "workspaceId": "ws_…",
    "externalUserId": "user_8812",
    "platforms": ["twitter", "linkedin"],
    "redirectUrl": "https://app.example.com/settings/social",
    "branding": { "name": "Acme", "logoUrl": "https://app.example.com/logo.png" }
  }'
```

The response carries a `url`. Send your user there: they see your name and logo, pick a network from `platforms`, and authorize it. The link stays open for one hour and is spent by the first account it connects.

- `externalUserId` is your id for that user. The connected account carries it, so `GET /v1/accounts?external_user_id=user_8812` finds their accounts.
- `redirectUrl` is where they land once connected, with `status=success`, `platform`, `account_id` and `external_user_id` appended. Its domain must be on the workspace redirect allowlist, set in the dashboard under **API Keys**; a domain that is not listed is refused, both when the link is created and again when it finishes.
- `workspaceId` can be omitted for a key bound to one workspace.
- `platforms` accepts the networks that connect in one step: `twitter`, `instagram`, `linkedin`, `threads`, `tiktok`, `youtube`, `reddit`, `tumblr` and `dribbble`. Networks that need a Page or board picked after authorizing are not available through a hosted link yet.

To learn the outcome without a redirect, poll the session:

```http
GET /v1/connect-sessions/{id}
```

`status` moves from `pending` to `used`, and `accountId` is set, once the user has connected. A session created in another workspace answers 404.

## Health

Tokens expire, users revoke apps, and networks change what a permission covers. Rather than discovering that at publish time, read health:

```http
GET /v1/accounts/health
GET /v1/accounts/{id}/health
```

The summary endpoint takes an optional `workspaceId` and reports every account at once, which is what you want on a dashboard or a morning check. A degraded account still publishes, with a warning. An expired or revoked one fails immediately.

```http
POST /v1/accounts/{id}/validate
POST /v1/accounts/{id}/refresh-token
```

`validate` calls the network and tells you whether the stored credentials still work. `refresh-token` forces a refresh ahead of schedule. Neither is normally necessary: tokens refresh on their own in the background, and this is for when you want to check before a launch rather than after.

## Analytics for one account

```http
GET /v1/accounts/{id}/analytics
```

Follower and engagement history for a single account. For cross-account reporting, use the [analytics endpoints](/api/analytics).

## Other operations

| Endpoint | What it does |
|:---------|:-------------|
| `GET /v1/accounts/{id}` | One account |
| `POST /v1/accounts/{id}/primary` | Mark the account primary for its platform |
| `DELETE /v1/accounts/{id}` | Disconnect. Published posts stay published |

## X communities

X accounts can post into communities, which have to be resolved before you can target one:

```http
GET    /v1/accounts/{accountId}/communities
GET    /v1/accounts/{accountId}/communities/search
POST   /v1/accounts/{accountId}/communities/sync
POST   /v1/accounts/{accountId}/communities/manual
DELETE /v1/accounts/{accountId}/communities/{communityId}
```

`sync` pulls the communities the account belongs to, `search` looks one up, and `manual` adds one by id when you already know it.

## Slack channels, members and identity

A Slack account connected through the app (not a webhook) has three extra resources:

```http
GET   /v1/accounts/{id}/slack/channels
GET   /v1/accounts/{id}/slack/members
GET   /v1/accounts/{id}/slack/identity
PATCH /v1/accounts/{id}/slack/identity
```

`channels` lists the channels the app can post to, with `is_current` on the one this account uses. `members` lists the people in the Slack workspace; a member's `id` is the handle for starting a DM. `identity` is the name and icon posts appear under:

```json
{ "username": "Release Bot", "icon_url": "https://yourbrand.com/bot.png" }
```

Omitted fields keep their value and `null` clears one. Set `icon_url` or `icon_emoji` (like `:rocket:`), not both. A webhook connection answers `409 webhook_connection`. All four need the `accounts` scope.

## Discord server

A Discord account connected as the bot (not a webhook) exposes the server it was installed into. Every route answers `409 webhook_connection` on a webhook connection, and `502` when Discord itself does not answer.

Channels and the posting identity:

```http
GET   /v1/accounts/{id}/discord/channels
PATCH /v1/accounts/{id}/discord/channels/current
GET   /v1/accounts/{id}/discord/identity
PATCH /v1/accounts/{id}/discord/identity
```

`channels` lists the text channels the bot can post to, with `is_current` on the one this account uses; `channels/current` takes `{ "channel_id": "..." }` and moves the account to another one in the same server. `identity` is the nickname and avatar the bot wears there:

```json
{ "username": "Release Bot", "avatar_url": "https://yourbrand.com/bot.png" }
```

Omitted fields keep their value and `null` clears one.

Messages, in the account's channel:

```http
GET    /v1/accounts/{id}/discord/messages/pinned
DELETE /v1/accounts/{id}/discord/messages/{messageId}
POST   /v1/accounts/{id}/discord/messages/{messageId}/pin
DELETE /v1/accounts/{id}/discord/messages/{messageId}/pin
POST   /v1/accounts/{id}/discord/messages/{messageId}/crosspost
POST   /v1/accounts/{id}/discord/messages/{messageId}/thread
POST   /v1/accounts/{id}/discord/dm
```

`crosspost` publishes an announcement-channel message to every server following the channel. `thread` takes `{ "name": "...", "auto_archive_duration": 1440 }`. `dm` takes `{ "member_id": "...", "content": "..." }` and sends one message to that member.

Scheduled events, members and roles:

```http
GET    /v1/accounts/{id}/discord/events
POST   /v1/accounts/{id}/discord/events
GET    /v1/accounts/{id}/discord/events/{eventId}
PATCH  /v1/accounts/{id}/discord/events/{eventId}
DELETE /v1/accounts/{id}/discord/events/{eventId}
GET    /v1/accounts/{id}/discord/members
GET    /v1/accounts/{id}/discord/members/{memberId}
GET    /v1/accounts/{id}/discord/roles
POST   /v1/accounts/{id}/discord/roles
PATCH  /v1/accounts/{id}/discord/roles/{roleId}
DELETE /v1/accounts/{id}/discord/roles/{roleId}
PUT    /v1/accounts/{id}/discord/roles/{roleId}/members/{memberId}
DELETE /v1/accounts/{id}/discord/roles/{roleId}/members/{memberId}
```

An event names either a `channel_id` (a voice or stage channel) or a `location` with an `end_time`:

```json
{
  "name": "Launch stream",
  "start_time": "2026-10-01T18:00:00Z",
  "end_time": "2026-10-01T19:00:00Z",
  "location": "https://yourbrand.com/live"
}
```

`members` takes `q` to search by username or nickname prefix, and `limit`. A member's `id` is the `member_id` for a DM and for a role assignment.

Everything here needs the `accounts` scope. The routes that put something on the server — deleting, pinning, unpinning, crossposting, starting a thread and sending a DM — need the `publish` scope as well.
