Media endpoints use the `posts` scope, because media only exists to end up on a post.

## Upload

```http
POST /v1/media/upload
```

Send `multipart/form-data` with the files under the `files` field:

```bash
curl -X POST https://api.fopost.com/v1/media/upload \
  -H "X-API-Key: $FOPOST_API_KEY" \
  -F "files=@launch.png" \
  -F "workspaceId=7d2b8c11-4e5a-4a8f-b0d9-3c5e6f7a8b90"
```

| Limit | Value |
|:------|:------|
| Files per request | 5 |
| Size per file | Your account's limit, at most 100 MB on this route |
| Types | jpeg, png, gif, webp, mp4, mov, webm, pdf, txt, csv |

The declared type is verified against the actual file contents, so renaming an executable to `.png` does not get it through.

This route carries the whole request through the API's edge, which refuses any request body over 100 MB before it reaches FoPost. A file that large on this route gets the edge's own `413` page, not a FoPost error, so keep multipart under 100 MB per file and send anything bigger through [direct upload](#direct-upload), which has no such cap. Within 100 MB, a file over your account's limit answers `413` with `file_too_large` and `max_file_bytes`.

Pass `workspaceId` to also save the files to that workspace's media library, where they are reusable and count against the account's storage allowance. Leave it out for a one-off attachment.

## Limits

```http
GET /v1/media/limits?workspaceId=7d2b8c11-4e5a-4a8f-b0d9-3c5e6f7a8b90
```

The largest file your account can upload grows with the number of connected accounts on the billing account:

| Connected accounts | Largest file |
|:-------------------|:-------------|
| Up to 2 | 100 MB |
| Up to 7 | 400 MB |
| Up to 15 | 2 GB |
| 16 and more | 5 GB |

The **Large Uploads** add-on (Settings → Billing) lifts any account to 5 GB for a flat monthly fee. The endpoint answers the ceiling in force, what set it, the multipart ceiling, and whether direct upload is available:

```json
{
  "data": {
    "maxFileBytes": 419430400,
    "source": "accounts",
    "connectedAccounts": 5,
    "largeUploadsEnabled": false,
    "nextTier": { "upToAccounts": 15, "maxFileBytes": 2147483648 },
    "multipartMaxFileBytes": 104857600,
    "maxFilesPerUpload": 5,
    "directUploadAvailable": true,
    "allowedTypes": ["image/jpeg", "image/png", "..."]
  }
}
```

Read it before an upload to pick the route and to show the person the real number. `source` is `accounts`, `add_on`, or `bypass`.

## Direct upload

For anything over 100 MB, or a client that should not proxy bytes through your server, upload straight to storage through a signed URL. The bytes never pass through the API, so the only ceiling is your account's limit, up to 5 GB in one PUT. It is three calls.

**1. Sign the upload.**

```http
POST /v1/media/presign
```

```json
{
  "workspaceId": "7d2b8c11-4e5a-4a8f-b0d9-3c5e6f7a8b90",
  "filename": "launch.mp4",
  "mimeType": "video/mp4",
  "size": 18350080
}
```

`folderId`, `brandRole`, `brandVoiceId`, `personConsent`, and `origin` are accepted here too, with the same meaning as on upload, so the finished item lands exactly where a multipart upload would.

```json
{
  "data": {
    "uploadId": "b1a3…",
    "uploadUrl": "https://…",
    "method": "PUT",
    "headers": { "Content-Type": "video/mp4" },
    "expiresAt": "2026-09-19T14:00:00.000Z",
    "maxFileBytes": 419430400
  }
}
```

The same types apply as for upload, `size` is checked against your account's limit (`413` `file_too_large` when over), and the storage allowance is checked here too. `size` is part of the signature, so the PUT is refused if the byte count differs.

**2. PUT the bytes.**

```bash
curl -X PUT "$UPLOAD_URL" -H "Content-Type: video/mp4" --data-binary @launch.mp4
```

Send exactly the returned headers and no API key. The URL accepts one PUT and stops working after an hour.

**3. Complete it.**

```http
POST /v1/media/presign/{uploadId}/complete
```

Completion verifies the object where it sits and promotes it into the library with the same checks as an upload: allowed type, content matching the declared type, size, storage allowance. It answers with the same item shape as upload, including `previewUrl`. A refused object is deleted; `409` means the upload was already completed and `410` that it expired. An upload that is never completed is discarded after 24 hours and never appears in the library.

The SDKs wrap all three calls in one helper (`media.uploadDirect` or the language equivalent).

## List the library

```http
GET /v1/media
```

Returns the workspace's library items with their type, name, size, and URL.

## Delete

```http
DELETE /v1/media/{id}
```

Removes the item from the library. Posts that already published with it are unaffected, since the network holds its own copy.

## Attaching to a post

Two ways. A post can carry its files in the same request: send `POST /v1/posts` (or `PUT /v1/posts/{id}`) as `multipart/form-data` with the JSON body in a `post` field and the files under `files`. They are stored in the workspace library and attached to the first content block. The multipart ceiling of 100 MB per file applies; see [publishing](/api/publishing#create-a-post-with-files).

Or upload first and take what upload returns into a content block:

```json
{
  "content": [
    {
      "text": "Doors open Monday.",
      "media": [
        {
          "type": "image",
          "name": "launch.png",
          "url": "https://...",
          "alt": "A storefront with the lights coming on"
        }
      ]
    }
  ]
}
```

`type` is `image`, `video`, or `gif`. `alt` is optional and worth sending: it is what screen readers announce, and several networks surface it.

Each network sets its own limits on count, dimensions, aspect ratio, and duration. FoPost resizes and re-encodes for the target where it can, and [preflight](/api/publishing#check-before-you-publish) tells you when it cannot.

## Storage

The library counts against your account's free storage allowance; past it, storage is metered per GB per month with a card on file. A stored URL is an identity, not public access: the bucket is private, and the dashboard renders media through a per-request check rather than a link anyone can pass around.
